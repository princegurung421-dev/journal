Week 6

Flask Backend Integration & Frontend-Backend Connection

December 2025 Flask & Backend

This week focused on integrating Flask as a backend framework for the Learning Journal PWA. The primary goal was to establish a connection between the frontend (browser interface) and backend (server) to transform the PWA from a static, local document into a dynamic, persistent web application. I implemented RESTful API endpoints using Flask and connected them to the frontend using JavaScript's Fetch API.

Why is the frontend–backend connection important?

The connection between the frontend (the browser interface) and the backend (the server) is essential because it moves the PWA from being a static, local document to a true, dynamic application. Before this lab, my journal entries were only saved to my browser's localStorage. That data was locked to that specific computer and browser; it wasn't persistent or shareable. The backend, built with Flask, provides the persistence by saving the data to a file (reflections.json) on the server. This makes the application useful because the data is now secure, available from any device, and can be managed centrally, which is the whole point of a web application.

Which HTTP methods did you use in Flask, and why?

I implemented three HTTP methods in my Flask backend: GET, POST, and DELETE.

  • GET was used for retrieving data. When the PWA loads, the JavaScript makes a GET request to /api/reflections to load and display all saved journal entries.
  • POST was used for creating new data. When I submit the journal form, the JavaScript sends a POST request with the new entry's data to /api/add_reflection to save it to the reflections.json file.
  • DELETE was used for my extra feature. It's the correct method for telling the server to remove a specific entry from the data file.

What is the difference between using Flask to store and load JSON data and reading JSON directly in the browser?

The main difference is about data management and persistence.

When reading JSON directly in the browser (or using localStorage), the data is client-side. The browser handles everything. This is simple, but the data isn't persistent across devices and can't be shared. Any changes are local.

By using Flask, the data is server-side. The browser only sends a request to the server, and Flask manages the data file (reflections.json). This ensures the data is persistent, safe, and available to anyone accessing the application. It shifts the responsibility for data integrity and security away from the user's device and onto the controlled server environment.

Did you face any difficulties when running your project on PythonAnywhere? How did you handle them?

I definitely hit a few snags, mostly related to file paths.

My biggest issue was the paths for my static assets (CSS/JS). When I first loaded the page, it was just plain HTML because the server couldn't find my stylesheet and script files. I initially used relative paths like href="css/style.css", but Flask requires template rendering. I solved this by going into my HTML file and replacing all the static file links with the correct template syntax: {{ url_for('static', filename='css/style.css') }}. After changing all the links and remembering to reload the web app in the PythonAnywhere 'Web' tab, the styles finally loaded.

What extra feature did you build into your PWA with Flask, and why did you add it?

For the extra feature, I added the ability to Delete an existing reflection.

To implement this, I had to update two things: first, I added a "Delete" button next to every reflection in the frontend. Second, I created a new @app.route() in flask_app.py that specifically handled the DELETE request. The JavaScript now sends a fetch request using the DELETE method along with a unique identifier for the reflection. This backend route removes that entry from the list and overwrites the reflections.json file.

I chose the delete feature because a journal is a personal tool that requires maintenance. If I accidentally make a duplicate entry or write something that's no longer relevant, I need a way to clean up the data. It was essential for moving my PWA toward a fully functional and practical application.

Key Learnings

  • Flask's route decorators make API creation straightforward and intuitive
  • RESTful design principles improve API usability and follow web standards
  • Fetch API enables seamless frontend-backend communication
  • Template rendering with url_for() is essential for Flask static file serving
  • Server-side data management provides persistence and security advantages
  • PythonAnywhere deployment requires proper file structure and WSGI configuration
  • HTTP methods (GET, POST, DELETE) have specific semantic meanings in REST APIs

Week 7

PWA Enhancement & Offline Support

December 2025 PWA & Service Workers

This week focused on transforming the Flask-powered Learning Journal into a full Progressive Web App (PWA) with offline access, installability, and improved user experience. I implemented a service worker, added a manifest file, and integrated caching strategies to ensure that users can still access previous reflections even when they are offline.

Why is it useful to enhance your Flask app with PWA features?

Adding PWA features makes the Flask app feel like a native application. The user can install it on their home screen, open it in full-screen mode, and continue using the app even without an internet connection. This is especially valuable for a journal application, since reflections should always be accessible. PWAs improve reliability, speed, and user engagement without needing a full mobile app.

What did you use to support offline access and dynamic data?

I implemented a service worker with two caching strategies:

  • Cache First for static assets such as CSS, JS, fonts, and images
  • Network First for the dynamic reflections API so users see the latest data but still get offline fallback

I also created a manifest.json, which provides icons, app name, short name, colors, and display mode. Together, these PWA technologies allow the app to work offline, load faster, and behave like a native mobile app.

What extra feature did you add, and why?

For this week’s extra feature, I added Offline Reflection Creation.

When the user is offline and tries to submit a reflection, the entry is saved to localStorage with a “pending” status. When the device reconnects, a small background script automatically syncs the pending reflections to the Flask backend using the POST API.

I added this because it prevents data loss and allows users to keep journaling without worrying about their network status. It makes the PWA much more durable and user-friendly.

Did you face any challenges deploying your PWA, and how did you solve them?

Yes, deployment brought two main issues:

  • Service Worker Not Updating: PythonAnywhere aggressively cached old files. I solved this by adding a version number to the cache name and using self.skipWaiting() to force the new service worker to activate.
  • HTTPS Requirement: PWAs require HTTPS for service workers. Luckily, PythonAnywhere automatically provides HTTPS, but I had to update all absolute URLs to make sure everything loaded securely.

After clearing the old cache in the browser and reloading the app, the PWA worked as expected.

What's Next: Integrating database support (SQLite or PostgreSQL), adding user authentication, and improving sync features for a more scalable version of the Journal app.

Intro

Introduction

This portfolio documents how I built my Learning Journal, a Progressive Web App for the Mobile Application Development unit. My aim was to start from a plain HTML and CSS website and grow it, week by week, into a full app that works online and offline, can be installed on a phone, and talks to a Python server. Along the way I learned responsive mobile-first layouts, JavaScript and the DOM, then APIs, storing data in JSON with Python, and finally connecting a Flask backend and adding PWA features like a manifest and a service worker.

The biggest thing I learned is how all these layers fit together — the browser, the storage, the server and the offline cache. The hardest part was making the PWA install correctly and deploying the whole app to PythonAnywhere rather than just the front page. I also added a Tic-Tac-Toe game as my mini project. This report reflects on each lab, the choices I made, the problems I ran into, and how I solved them.

Lab 1

Introduction to Mobile App

In the first lab I set up the tools I would use for the rest of the unit. I installed VS Code as my editor because it is free and supports HTML, CSS, JavaScript and Python well. I created a GitHub account and a repository for my Learning Journal so I could save my work and keep a history with commits, and I learned the add, commit and push workflow that I used every week.

I also set up a PythonAnywhere account, which is where my finished app runs online because it can host Python and Flask. I looked at Android Studio and some basic Kotlin code to understand how native Android apps are built, which helped me see why a PWA is a lighter alternative — it runs in the browser but can still be installed like an app.

My main challenge was getting comfortable with Git. At first I did not understand the difference between committing locally and pushing to GitHub, and once my code was only on my computer. I fixed this by checking git status and pushing regularly, and I set up an SSH key so I could push securely without typing my password each time. By the end of the lab I had a working setup: an editor, a version-controlled repository, and a hosting account ready for the later labs.

Lab 2

Frontend Fundamentals

How did you approach mobile-first design?

I wrote my base CSS for small phone screens first, then added media queries (@media (min-width: 768px)) to adjust the layout for larger screens. For example, my navigation is a fixed bottom bar on mobile and becomes a sidebar on desktop. Designing for the smallest screen first meant the important content always fit, and scaling up was easier than squeezing a desktop design onto a phone.

What was the most useful HTML or CSS concept you applied this week?

The most useful concept was Flexbox together with CSS variables. Flexbox made it simple to line up items like my nav icons and cards without lots of floats. CSS variables such as --brand and --bg let me define my colours once and reuse them everywhere, which later made adding a light and dark theme easy — I just swapped the variable values.

What part of HTML or CSS did you find most challenging or confusing?

The most confusing part was making the navigation responsive. I wanted a vertical sidebar on desktop but a fixed bottom bar on mobile, and switching between them with media queries kept breaking the spacing. I also hit CSS specificity issues where styles were overridden unexpectedly. I solved it by using the browser DevTools to inspect which rules applied and by keeping my selectors simple.

Lab 3

JavaScript & DOM Manipulation

Which DOM selection methods did you use, and why did you choose them?

I mainly used document.getElementById() and document.querySelector()/querySelectorAll(). I used getElementById for single, known elements like the clock and the reflection form fields, because it is fast and clear. I used querySelectorAll when I needed several elements at once, such as all the nav links or all the accordion headers, so I could loop through them and add event listeners.

What was the most challenging part about linking JavaScript with your HTML?

The hardest part was making sure my JavaScript ran after the HTML existed. At first I put scripts in the head and the code could not find elements because they had not loaded yet. I fixed this by putting scripts at the end of the body and using the DOMContentLoaded event. Making the IDs and class names match exactly between the HTML and the JS also took care.

How did you test and debug your JavaScript code?

I tested mostly with the browser DevTools. I used console.log() to check values, the Console tab to read error messages, and the Elements tab to see if my classes were toggling. For the offline features I used the Network tab to switch to Offline and confirm the app still worked. Reading the red console errors line by line helped me find typos and wrong selectors.

Lab 4

API

Which Storage, Browser, and Third-Party APIs did you choose, and why?

For storage I used the Web Storage API (localStorage) to remember the theme, and IndexedDB to store reflections written offline. For a browser API I used the Intl API to show the user's time zone and a live clock, plus navigator.onLine to detect the connection. For a third-party API I used the YouTube IFrame Player API to embed and control a video on my Projects page.

How did you integrate each API with DOM manipulation?

Each API updates the DOM. The clock writes the time into a element every second with textContent. The saved theme is applied by setting a data-theme attribute on the page. Reflections from IndexedDB and the server are turned into HTML cards and inserted with innerHTML. The YouTube API loads a player into a chosen element and my Play/Pause buttons call its methods.

What challenges did you encounter, and how did you solve them?

My biggest challenge was the location feature. I first used the Geolocation API, but it showed a permission popup every time and needed a network call to get the place name, which felt intrusive and did not work offline. I solved it by switching to the Intl time zone, which gives the user's city and GMT offset instantly, with no popup and no network.

In what ways do these APIs improve your Learning Journal PWA?

They make the app feel alive and personal. The clock and time zone give real-time context, the theme storage remembers the user's preference between visits, IndexedDB lets people keep writing when offline, and the YouTube embed adds useful learning content. Together they turn a static website into an interactive app that responds to the user and their device.

Lab 5

Python & JSON

How is storing data in a JSON file different from using browser storage?

A JSON file on the server is shared and permanent — every visitor sees the same data and it stays after the browser is closed. Browser storage like localStorage or IndexedDB is private to one device and one browser, so another user or computer would not see it. The JSON file is good for content everyone should see; browser storage is good for personal or offline data.

How did you use Python to create or update your JSON file?

I wrote a Python script (save_entry.py) that opens reflections.json, loads it with the json module into a list, adds a new reflection as a dictionary, and writes it back with json.dump(). Later my Flask app does the same inside its API routes — it reads the file, inserts or removes an entry, and saves it again, so the JSON file is always up to date.

What does your PWA show locally, and what will users see on GitHub? Are they the same?

They are not the same. On my computer the Flask server runs, so I can add and delete reflections and the JSON file updates. On GitHub Pages only the static files are served — there is no Python running, so the API calls fail and saving does not work. That is why I deployed the full app to PythonAnywhere, which can run the backend, and use GitHub only to store the code.

What extra feature did you add to your PWA using the JSON file, and why?

I added an export and import feature. The user can download all their reflections as a JSON file to back them up, and import a JSON file to restore them. I added this because the data is already in JSON, so it was a natural way to let users keep their own copy and move it between devices.

Lab 6

Frontend & Backend

Why is the frontend–backend connection important?

The connection lets the app do things the browser alone cannot. The front end handles what the user sees and clicks, while the back end stores data permanently and shares it between users and devices. Without the backend, reflections would only live in one browser. Connecting them means a reflection I save is written to the server and is still there when I reopen the app anywhere.

Which HTTP methods did you use in Flask, and why?

I used GET and POST. GET is for reading data — my page calls GET /api/reflections to load all entries. POST is for sending data — POST /api/save_reflection adds a new one and POST /api/delete_reflection removes one. I used POST for delete instead of the DELETE method because some hosts block DELETE, and POST works reliably everywhere.

What is the difference between using Flask to store and load JSON data and reading JSON directly in the browser?

Reading JSON directly in the browser is read-only — the browser can fetch the file but cannot change it. With Flask the server can both read and write the file, so the app can actually add and delete data. Flask also runs the logic in one central place, so all users share the same up-to-date data instead of each having a separate copy.

Did you face any difficulties when running your project on PythonAnywhere?

Yes. At first only the static journal worked online, because I had used Python's simple http.server, which does not run properly on PythonAnywhere. I fixed this by rewriting the backend as a Flask app. I then pointed PythonAnywhere's WSGI file at my app.py, cloned the code from GitHub with git clone, and reloaded the web app. Getting the file path right in the WSGI file was the main fix.

What extra feature did you build into your PWA with Flask, and why did you add it?

With Flask I added server-side saving and deleting of reflections through a REST API, so entries persist for everyone, not just in one browser. I also made Flask serve the whole app — every page, the manifest and the service worker — from one place, which keeps the front end and API on the same origin and makes the fetch calls simple and reliable.

Lab 7

PWA

Why is it useful to enhance your Flask app with PWA features?

PWA features make my Flask app behave like a real mobile app. Users can install it on their home screen, open it in its own window without the browser bar, and still use it when the network is poor or gone. This improves reliability and the experience, while I keep the simplicity of building with web technologies and one Flask server.

What did you use to support offline access and dynamic data?

For offline access I used a service worker with the Cache API to store the pages, CSS, JS and icons, so the app loads without a network. For dynamic data I used IndexedDB to save reflections written offline, and navigator.onLine with online/offline events to detect the connection. When the connection returns, my code syncs the saved entries to the Flask server automatically.

What extra feature did you add, and why?

My extra PWA feature is automatic offline sync with a status toast. If I write a reflection while offline it is stored in IndexedDB and shown with an "offline / pending" badge. When the device reconnects, a small toast appears, the entry is sent to the server, and the badge clears. I added this so users never lose work and can see what is happening.

Did you face any challenges deploying your PWA, and how did you solve them?

Yes. The app would not install — the browser said the manifest had no valid icon. I found the manifest pointed to icon files that did not exist, so I created proper 192px and 512px PNG icons plus a maskable icon, and the install prompt then appeared. I also had to serve everything over HTTPS on PythonAnywhere, which browsers require before a PWA can be installed.

Mini Project

Tic-Tac-Toe Game

What additional features did you add to your Learning Journal?

For my mini project I added a Tic-Tac-Toe game. It is a two-player game built with the DOM: a three-by-three grid of cells that players click to place X or O. The game tracks whose turn it is and shows it above the board, checks after every move for the eight winning lines, and highlights the winning row with a pulsing animation. If all cells fill with no winner it declares a draw, and a Restart button clears the board. I styled the board to match the rest of the app, using the same navy and coral theme and the light and dark modes, and made it responsive so the cells shrink to fit a phone. Beyond the game, the wider journal gained several features that support the main app: writing and deleting reflections through a form, searching them by keyword, exporting and importing them as JSON, a live clock and time zone, a light/dark theme, and offline saving with automatic sync. Together these turn a simple journal into an interactive app with a bit of fun built in.

Why did you choose your mini project idea?

I chose Tic-Tac-Toe because it was a realistic size for the four weeks I had, but it still let me show real programming skills rather than just copying a tutorial. It uses the same DOM and event-handling ideas I learned earlier in the unit — selecting elements, listening for clicks and updating the page — so it built naturally on my existing knowledge instead of needing a whole new technology. A game also fits the theme of a learning journal: it gives the user a short, enjoyable break between writing reflections, which makes the app more engaging. Tic-Tac-Toe has clear, simple rules, so I could focus my effort on writing clean logic — tracking turns, detecting a win across rows, columns and diagonals, and handling a draw — and on making the interface look good and work on mobile. It was also a good way to practise keeping game state in JavaScript and reflecting that state back into the DOM. Finally, it was something I could finish and polish properly, which mattered because a small feature that works well shows more skill than a large one left broken.

What technical challenges did you face and how did you solve them?

The trickiest part of the game was the win-checking logic. I stored the board as an array and had to compare the right combinations of cells for all eight winning lines, while making sure the game stopped once someone won. I fixed this by writing a list of the winning index patterns and looping through them after each turn, then disabling further clicks when a win or draw was found. Matching the game to the rest of the app was another challenge, because it originally used hard-coded teal colours that clashed after I changed the theme; I replaced those with the shared CSS variables so the game follows the light and dark themes automatically. Outside the game, the hardest overall challenge was the PWA install failing because the manifest referenced icons that did not exist — I created the missing icons and it worked. Deployment was also difficult: at first only the journal worked online because I had used a simple Python server, so I rewrote the backend in Flask and deployed it to PythonAnywhere from GitHub. Testing offline in DevTools helped me confirm each fix.

What would you improve if given more time?

If I had more time I would add user accounts so each person has their own private reflections behind a login, instead of everyone sharing one file. I would move the data from a JSON file into a proper database like SQLite, which would handle many entries more safely and make searching faster. For the game, I would add a single-player mode against the computer, a scoreboard that remembers wins, and sound effects. I would also improve accessibility — better keyboard navigation, focus styles and screen-reader labels — so more people can use the app comfortably. On the PWA side I would add push notifications to remind users to write a reflection, and background sync so pending entries send even after the app is closed. Finally, I would write automated tests for the API and the game logic so I could change the code with more confidence, and spend more time on the visual design and animations. These changes would take the project from a strong coursework app towards something closer to a real product.
